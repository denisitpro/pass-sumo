# KDBX interop fixtures

Golden `.kdbx` files produced by **KeePassXC** (a different, trusted implementation), so
pass-sumo's own KDBX codec can be tested against real-world files instead of only against
itself. Generated by [`../../scripts/make-fixtures.sh`](../../scripts/make-fixtures.sh); verified
by hand with `keepassxc-cli` (see "Verification" below) and re-verifiable any time with
[`../../scripts/interop-check.sh`](../../scripts/interop-check.sh).

Tool used: `keepassxc-cli`, version **2.7.12** (`/Applications/KeePassXC.app/Contents/MacOS/keepassxc-cli`,
also reachable via a Homebrew-installed symlink of the same binary at `/opt/homebrew/bin/keepassxc-cli`
on the machine these were generated on — confirmed identical file, not a different build).

> **Warning**: the master password for every fixture below is published right here:
> `correct horse battery staple`. These are test files with no real secrets. Never reuse
> this password for anything real, and never treat these files as a template for how to
> store an actual database.

## The CLI cannot select KDBX format version, KDF, or cipher — at all

The task this fixture set was built for asks for KDBX 4.x files in four KDF/cipher
combinations (Argon2d+AES256, Argon2id+AES256, Argon2d+ChaCha20, AES-KDF+AES256-in-KDBX4)
plus a KDBX 3.1 file. **None of the four KDBX4 combinations could be produced.** This was
not a guess — it was verified directly against the installed binary:

- `keepassxc-cli db-create --help`, `db-edit --help`, and `import --help` were read in full.
  None of them has a flag for KDF algorithm, cipher, or format version — only
  `--set-key-file`/`-k`, `-p`/`--set-password`, `-t`/`--decryption-time` (which only tunes
  AES-KDF's round count, see below), and (for `db-edit`) `--unset-key-file`/`--unset-password`.
- Every database created by `db-create` or `import`, with or without `-t`, decodes (checked
  byte-for-byte with a small Python header parser) to KDBX format version **3.1**, cipher
  **AES 256-bit**, KDF **AES-KDF** — confirmed both via the raw header bytes and via
  `keepassxc-cli db-info`.
- Invented flag names were probed directly against `db-create` and every one came back
  `Unknown option`: `--kdf`, `--cipher`, `--algorithm`, `--format`, `--kdbx4`,
  `--kdbx-version`, `--argon2`, `--argon2id`, `--chacha20`.
- The GUI application (strings extracted from the `keepassxc-cli` binary itself) clearly
  supports all of "AES-KDF (KDBX 3)", "AES-KDF (KDBX 4)", "Argon2d (KDBX 4)", "Argon2id
  (KDBX 4)" and format selection ("KDBX 3" vs "KDBX 4 (recommended)") in its Database
  Security Settings dialog — but those are GUI-only strings; `keepassxc-cli` has no
  command-line surface for any of it.

**Conclusion:** with this CLI, every database it creates is KDBX 3.1 + AES-KDF + AES-256,
unconditionally. There is no way to produce a KDBX4 file, of any KDF/cipher combination,
from `keepassxc-cli` alone. If a future test genuinely needs a real KDBX4 fixture from a
third-party tool, it will have to come from the KeePassXC **GUI** (its New Database wizard
and Database Security Settings dialog do expose all of this) or from a different CLI tool —
out of scope for this script, which is CLI-only by design.

This also means our "KDBX 3.1" and "AES-KDF + AES-256" requirements collapse into the same
file: there is only one reachable point in the whole requested matrix, not two.

## Low KDF parameters (deliberately weak — test fixtures only)

All fixtures use AES-KDF with **1,000,000 rounds** — `keepassxc-cli`'s fixed built-in
default when `db-create`/`import` are called *without* `-t/--decryption-time`. This was a
deliberate choice, not an oversight: passing the *minimum* allowed `--decryption-time`
(100 ms — the CLI rejects anything below that) actually benchmarked to a **higher** round
count (13,043,478 rounds, ~127 ms to unlock) on the machine these fixtures were built on,
because that flag targets a wall-clock time, not a round count, and this hardware is fast.
Omitting `-t` entirely and taking the CLI's fixed default is therefore the *fastest*
(lowest-latency) option `keepassxc-cli` can produce — it unlocked in ~25 ms in testing.
1,000,000 AES-KDF rounds is still weak by current standards (that's the point — CI must
stay fast), but is nowhere near instant, so it also exercises the codec's real KDF path
rather than a degenerate zero-round case.

### `kdbx3-corrupted.kdbx`

- Byte-for-byte identical to `kdbx3-aeskdf-aes256.kdbx` except for **one flipped byte**,
  intended to make the decoder's integrity check fail.
- **Corrupted offset:** absolute byte offset **322** in the file (header ends at offset
  222 for this particular file — the offset is `header_end + 100` and is recomputed by
  the script each run by parsing the real TLV header, so it will differ slightly if the
  content changes; check the script's own printed `header_end=`/`corrupted_byte_offset=`
  output when regenerating). The byte at that offset was XORed with `0xFF`.
- **Important nuance — KDBX 3.1 has no HMAC.** Per-message-block HMAC-SHA256 authentication
  is a KDBX4 feature. KDBX 3.1's integrity mechanism is different: (1) a 32-byte
  `StreamStartBytes` value, stored in the header and re-checked against the first 32 bytes
  of the decrypted body, which mostly exists to give a fast "wrong password" signal, and
  (2) a `HashedBlockStream` layer that SHA-256-hashes each block of the (decompressed)
  body. Where exactly the flipped byte lands changes the *observed* error:
  - **Within the first 32 decrypted bytes** (i.e. absolute offset 222–253 for this file):
    produces `Invalid credentials were provided, please try again.` — indistinguishable
    from a wrong password, because AES-CBC decryption scrambles that entire first block.
  - **Past that point** (the offset actually used here, absolute 322): produces
    `Error while reading the database: No root group`. This build of `keepassxc-cli`
    does **not** surface a distinct "block hash mismatch" message for this kind of
    corruption (its two known strings for that, `Invalid hash size.` / `Invalid hash of
    final block.`, were not observed to trigger at this offset) — instead, the corrupted
    bytes decompress to garbled XML that fails to parse into a valid document, and the
    generic "no root group found" error surfaces instead. **Document this precisely if you
    rely on it**: do not assume `keepassxc-cli`'s error text for a corrupted KDBX3 file
    says anything about hashes or HMACs. Our own codec's expected behavior for this file
    is an integrity/corruption error (however we choose to name it), not `wrongCredentials`
    — see the wrong-password note below for the distinction we do expect our codec to make.
- **Password:** `correct horse battery staple` (the file cannot actually be opened with any
  password, correct or otherwise, once corrupted this way).

### Wrong password (no separate file)

Not shipped as a distinct fixture — per the task, this is a behavior to assert against any
of the good fixtures above, using the right password's file with a wrong password string.
`keepassxc-cli` itself reports `Error while reading the database: Invalid credentials were
provided, please try again. If this reoccurs, then your database file may be corrupt.` and
exits non-zero for this case (verified against `kdbx3-aeskdf-aes256.kdbx`). Our own codec is
expected to classify this specific case as `wrongCredentials` — distinct from the corrupted-file
case above, even though (as documented there) KDBX 3.1's own error reporting sometimes cannot
tell the two apart itself when the corruption happens to land in the early verification bytes.

## TOTP: KeePassXC's real storage convention

Verified by hand: exported a `GitHub` entry to XML, added a single `<String>` field named
`otp` whose value is a full `otpauth://` URI, re-imported it, and ran
`keepassxc-cli show ... --totp`, which produced a live, changing 6-digit code. This
confirms KeePassXC's actual convention is:

```xml
<String>
    <Key>otp</Key>
    <Value>otpauth://totp/GitHub:alice?secret=JBSWY3DPEHPK3PXP&amp;issuer=GitHub&amp;algorithm=SHA1&amp;digits=6&amp;period=30</Value>
</String>
```

A single plain (not memory-protected) string field named `otp`, holding the entire
`otpauth://totp/...` URI as its value — **not** the older split `TOTP Seed` / `TOTP Settings`
fields (that was the convention used by the old `keepassx`/keepass2-android "TOTP" plugin
predating this). Our codec's TOTP interop should read/write the `otp` field with an
`otpauth://` URI to match real KeePassXC databases.

## Custom fields: protected vs. plain, confirmed round-trip

KeePassXC's XML export represents a memory-protected string field with a `Protected` flag
as an XML *attribute* on the `<Value>` element (`ProtectInMemory="True"`), with the value
still stored as plain text in the export (the export format is a plaintext backup format;
the actual in-line-memory / on-disk protected-stream obfuscation is applied by KeePassXC
internally when it re-encodes the field into the binary `.kdbx` container, not something the
XML export/import round-trip needs to represent itself). Confirmed both directions: a hand-added
`<String><Key>Security Answer</Key><Value ProtectInMemory="True">...</Value></String>` field
survived import and reported `PROTECTED` under a plain `show --all`, then the real cleartext value
under `show --all -s` (`-s`/`--show-protected`).

## Regenerating

```sh
PassSumo/scripts/make-fixtures.sh
```

Deletes and rebuilds every `.kdbx`/`.key` file in this directory from scratch (this
README is hand-maintained and is left untouched). Requires `keepassxc-cli` (PATH or the
default macOS `.app` bundle path) and `python3` (used only for XML text-splicing — setting
custom string fields and the `otp` field — and for the deliberate single-byte corruption;
`keepassxc-cli` itself has no CLI flag for either).

## Verifying

```sh
PassSumo/scripts/interop-check.sh <path-to-kdbx> <password> [keyfile]
```

Confirms a `.kdbx` file opens (`ls -R`) and exports as well-formed KeePassXC XML
(`export -f xml`) via `keepassxc-cli`, exiting non-zero on any failure. This is what CI
should run against a file *our own app* writes, to prove interop in the other direction.

# KDBX 4.x fixtures (`kdbxkit/`) — added by the KDBX codec owner

Everything above this line is generated/maintained by `make-fixtures.sh` and describes files
`keepassxc-cli` produced. This section covers a second, separate set with a different provenance,
added because — as the CLI section above establishes — `keepassxc-cli` cannot produce a KDBX 4
file at all, and KDBX 4 is pass-sumo's primary format.

## Provenance and license

These two files are copied verbatim from the test resources of **KDBXKit**
(`PassSumo/Vendor/KDBXKit`, vendored from upstream `shadone/KDBXKit` via `git subtree`), at the
exact revision this app pins, `e9b8839f1226b82665e1e4b7f12f13635d189deb`:

    Tests/KDBXKitTests/Resources/{simple-argon2id-aes256,kpxc-rich}.kdbx

KDBXKit is **BSD-2-Clause**, which covers redistribution of these files with the notice recorded in
[`../../../THIRD-PARTY-NOTICES.md`](../../../THIRD-PARTY-NOTICES.md). Their content was written by
KeePassXC and committed to that repository as interop fixtures.

## What they prove, and what they do not

**They are the library's own fixtures.** A test that only reads them is checking that our codec
agrees with KDBXKit about files KDBXKit was developed against — it cannot catch a bug the library
has agreed with itself about, because both the fixture and the parser come from the same author.
They are worth having (they are real KeePassXC output, and nothing else here is KDBX 4 at all), but
they are the weaker half of the evidence.

The strong half is the **write** direction, which does not depend on KDBXKit's judgement at all:
KDBXKit's writer always emits KDBX 4.1, and `keepassxc-cli` *can read* KDBX 4 even though it cannot
create one. So `KDBXCodecTests` writes a file with our own codec and then hands it to
`interop-check.sh` / `keepassxc-cli` for an independent verdict. That is the assertion that
actually proves interop.

## `kdbxkit/simple-argon2id-aes256.kdbx`

- **KDBX version:** 4.1 · **KDF:** Argon2id (10 iterations, 64 MiB) · **Cipher:** AES-256
- **Password:** `123`  *(verified by opening it with `keepassxc-cli ls -R`, not read off a
  test source)*
- Content: database `test2`, one entry `hello` in the root group. Minimal by design — the

## `kdbxkit/kpxc-rich.kdbx`

- **KDBX version:** 4.1 · **KDF:** Argon2id (10 iterations, 64 MiB) · **Cipher:** AES-256
- **Password:** `123`  *(verified the same way)*
- 3 groups (`Work`, `Work/Servers`, plus the root), 4 entries.
- Carries, in one file, everything the lossless round-trip test needs to assert survives a save:
  - a **binary attachment** (`notes.txt`) on the `GitHub` entry,
  - **entry history** — 3 prior snapshots on that same entry,
  - **`Meta/CustomData`** with two items (`_LAST_MODIFIED`, `KPXC_RANDOM_SLUG`) that no part of

  - `AutoType` blocks, non-ASCII titles/values (`Unicode 测试 🌍`, `汉字 + 🌸 + ñ`), and nested
    groups.
- It has **no** TOTP field and no custom string fields, so the TOTP assertions use
  `kdbx3-aeskdf-aes256.kdbx` (above) and a vault our own codec writes.

## Bundling

Both directories reach the test bundle through one folder reference declared in
`PassSumo/project.yml` (`PassSumoUnitTests` → `sources` → `Sources/UnitTests/Fixtures`,
`type: folder`). Structure is preserved, so a fixture is addressed as `Fixtures/<name>.kdbx` or
`Fixtures/kdbxkit/<name>.kdbx`. **Adding a fixture needs no project.yml change** — drop the file in
and it is bundled.

# TOTP-convention fixture (`totp/`) — added by the KDBX codec owner

## `totp/kdbx3-totp-conventions.kdbx`

- **KDBX version:** 3.1 · **KDF:** AES-KDF · **Cipher:** AES-256 (i.e. whatever
  `keepassxc-cli import` produces — see the CLI section far above)
- **Password:** `correct horse battery staple`
- Written by `keepassxc-cli 2.7.12 import` from
  [`totp/kdbx3-totp-conventions.source.xml`](totp/kdbx3-totp-conventions.source.xml), which is kept
  next to it so the fixture is reproducible:
  `keepassxc-cli import -p kdbx3-totp-conventions.source.xml kdbx3-totp-conventions.kdbx`
- Two root-level entries, one per TOTP storage convention **in the same file**:
  - `OtpURLStyle` — a single `otp` field holding a full `otpauth://totp/...` URI (current
    KeePassXC).
  - `SeedSettingsStyle` — the older split pair, `TOTP Seed` = `JBSWY3DPEHPK3PXP` and
    `TOTP Settings` = `30;6`.
- Both use the same secret, so KeePassXC produces the **same** code from both — verified on the
  built fixture: `keepassxc-cli show -t … /OtpURLStyle` and `… /SeedSettingsStyle` both returned
  `812258` in the same 30-second window. That is what establishes, empirically rather than from
  documentation, that KeePassXC 2.7.12 still reads the split form as well as `otp`.
- This is the fixture behind the codec's hard rule that a save **never rewrites one convention into
  the other**: `KDBXCodecTests` opens it, changes the *password* of the split-form entry, saves,
  reopens, and asserts the entry still stores its TOTP as `TOTP Seed` + `TOTP Settings` and that
  the URL-form entry still stores its as `otp`.
